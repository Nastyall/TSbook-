# 3. ОПИСАНИЕ ПРОЦЕССА РАЗРАБОТКИ

## 3.1 Разработка программного продукта

Разработка программного продукта TSBook включала в себя создание полнофункциональной веб-платформы для обмена и продажи книг между пользователями. Процесс разработки осуществлялся по методологии Agile с использованием итеративного подхода.

### 3.1.1 Технологический стек

**Frontend (клиентская часть):**
- **Next.js 14** — React-фреймворк с поддержкой серверного рендеринга
- **TypeScript** — типизированный JavaScript для повышения надёжности кода
- **Tailwind CSS** — утилитарный CSS-фреймворк для стилизации
- **React Context API** — управление состоянием приложения

**Backend (серверная часть):**
- **Django REST Framework** — веб-фреймворк для создания API
- **Python 3.11** — язык программирования
- **SQLite** — реляционная база данных
- **JWT (Simple JWT)** — аутентификация и авторизация

### 3.1.2 Структура приложения

Приложение состоит из следующих основных модулей:

1. **Модуль аутентификации** — регистрация, вход, управление профилем
2. **Модуль объявлений** — создание, редактирование, просмотр, поиск книг
3. **Модуль чатов** — обмен сообщениями между пользователями
4. **Модуль подписок** — подписка на пользователей, лента обновлений
5. **Модуль рейтингов** — оценки и отзывы о пользователях
6. **Модуль избранного** — сохранение понравившихся объявлений

## 3.3 Обеспечение безопасности информации

### 3.3.1 Анализ угроз

В процессе эксплуатации платформы TSBook возможны следующие угрозы безопасности:

**1. Угрозы конфиденциальности:**
- Перехват учётных данных при передаче
- Несанкционированный доступ к персональным данным
- Утечка данных через уязвимости в API

**2. Угрозы целостности:**
- Модификация данных злоумышленником
- SQL-инъекции
- XSS-атаки (Cross-Site Scripting)

**3. Угрозы доступности:**
- DDoS-атаки
- Перебор паролей (Brute-force)
- Злоупотребление API (Rate limiting)

**4. Угрозы аутентификации:**
- Кража сессионных токенов
- Подделка межсайтовых запросов (CSRF)
- Фишинг

### 3.3.2 Реализованные меры защиты

#### 3.3.2.1 Аутентификация и авторизация

**JWT-токены:**
- Использование access-токенов (срок жизни: 1 час)
- Использование refresh-токенов (срок жизни: 7 дней)
- Хранение токенов в localStorage с HttpOnly флагом
- Автоматическое обновление токенов при истечении

```python
# Настройки JWT в Django
SIMPLE_JWT = {
    'ACCESS_TOKEN_LIFETIME': timedelta(hours=1),
    'REFRESH_TOKEN_LIFETIME': timedelta(days=7),
    'ROTATE_REFRESH_TOKENS': True,
    'BLACKLIST_AFTER_ROTATION': True,
    'ALGORITHM': 'HS256',
    'SIGNING_KEY': SECRET_KEY,
}
```

**Парольная защита:**
- Минимальная длина пароля: 8 символов
- Хранение паролей в хешированном виде (PBKDF2)
- Проверка сложности пароля

#### 3.3.2.2 Защита от веб-уязвимостей

**SQL-инъекции:**
- Использование ORM Django с параметризованными запросами
- Валидация всех входных данных
- Санитизация пользовательского ввода

```python
# Безопасный запрос через ORM
book = Book.objects.filter(owner=self.request.user).first()
# Вместо опасного:
# book = Book.objects.filter(f"owner = '{user_input}'").first()
```

**XSS-атаки:**
- Автоматическое экранирование в шаблонах Django
- Content Security Policy (CSP) заголовки
- Sanitization HTML-контента

**CSRF-атаки:**
- CSRF-токены для всех форм
- Проверка заголовка Origin для API-запросов
- SameSite cookies

#### 3.3.2.3 Защита данных

**Шифрование:**
- HTTPS для всех соединений (TLS 1.3)
- Шифрование чувствительных данных в базе
- Хеширование паролей с солью

**Контроль доступа:**
- Разграничение прав доступа (IsAuthenticated, IsOwnerOrReadOnly)
- Проверка прав на каждое действие
- Логирование критических операций

```python
# Пример проверки прав доступа
class IsOwnerOrReadOnly(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        if request.method in permissions.SAFE_METHODS:
            return True
        return obj.owner == request.user
```

#### 3.3.2.4 Защита от злоупотреблений

**Rate Limiting:**
- Ограничение запросов к API: 100 запросов/минуту
- Ограничение попыток входа: 5 попыток/15 минут
- Блокировка при превышении лимита

**Валидация данных:**
- Проверка типа и размера загружаемых файлов
- Максимальный размер файла: 5 МБ
- Разрешённые типы: изображения (JPEG, PNG, GIF)

```python
# Валидация загружаемого файла
if not file.type.startswith('image/'):
    raise ValidationError('Только изображения разрешены')
if file.size > 5 * 1024 * 1024:
    raise ValidationError('Максимальный размер: 5 МБ')
```

### 3.3.3 Политики безопасности

#### 3.3.3.1 Хранение данных

| Тип данных | Срок хранения | Метод защиты |
|------------|---------------|--------------|
| Персональные данные | На время аккаунта | Шифрование |
| Сообщения чата | 1 год | Контроль доступа |
| Логи действий | 90 дней | Только чтение |
| Резервные копии | 30 дней | Шифрование |

#### 3.3.3.2 Управление доступом

**Ролевая модель:**

| Роль | Права доступа |
|------|---------------|
| Гость | Просмотр каталога, поиск |
| Пользователь | Все функции гостя + создание объявлений, чаты, избранное |
| Модератор | Все функции пользователя + модерация контента |
| Администратор | Полный доступ |

#### 3.3.3.3 Реагирование на инциденты

**Процедура при обнаружении уязвимости:**
1. Немедленное логирование инцидента
2. Изоляция затронутого компонента
3. Анализ причины уязвимости
4. Выпуск патча безопасности
5. Уведомление пользователей (при утечке данных)

### 3.3.4 Рекомендации по безопасности

**Для пользователей:**
1. Использовать сложные уникальные пароли
2. Включить двухфакторную аутентификацию (при наличии)
3. Не передавать учётные данные третьим лицам
4. Регулярно обновлять пароль
5. Проверять URL сайта перед вводом данных

**Для администраторов:**
1. Регулярно обновлять зависимости
2. Проводить аудит безопасности (ежеквартально)
3. Мониторить логи на предмет аномалий
4. Хранить резервные копии в защищённом месте
5. Ограничить доступ к серверу по SSH-ключам
